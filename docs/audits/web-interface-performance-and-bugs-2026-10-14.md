# Web Interface Performance, Memory And Bug Audit

Reviewed: **2026-10-14**. Source baseline:
`c5030ebf7ac6a5a62e2f4ff773ed4a7c7eda8f36` (`main`, admin-web package `0.8.7`).
This is an audit/backlog. Application behavior has not been changed.

The inventory contains **62 entries: 9 bugs, 8 investigation items and 45
optimization opportunities**. Scope is the browser account/admin interface in
`apps/admin-web`, its shared Teams components, and the server endpoints it calls.
An independent Android audit and a full server product audit remain separate.
Browser file editors and a full direct/group-chat inbox are not shipped by this
interface; their absence is planned product work, not a regression.

This is a comprehensive first-pass inventory, not proof that no additional
issue exists. Discovery inventoried 19 TS/TSX files, including tests, and 11,709
lines in admin-web. The 6,490-line `App.tsx`, asynchronous loads, permissions,
settings, transfer paths, account flows, shared channels and expensive server
operations received manual review. Production browser heap, network traces,
database plans and multi-user load measurements are still needed to rank costs.

## Reported Regression Follow-Up

The [2026-10-14 reported-issue reconciliation](./reported-regressions-2026-10-14.md)
tracks all 13 subsequent user reports against these inventories, including PDF
state reset, cache-first reads/automatic freshness, slow/basic previews, component
consistency, drop targeting, legacy chat/sidebar behavior, Kanban scrolling,
mobile drawing and canvas performance/save failures. Existing IDs/counts remain
unchanged; the supplement separates reported symptoms from verified mechanisms
and adds acceptance targets for gaps. Fixes and platform reproduction remain
outstanding.

## Evidence And Baseline

- **Reproduced** means a focused jsdom/React probe exercised current components
  or helpers with controlled network/storage behavior. Probes assert current
  behavior; they are not future acceptance tests. No live browser or assistive
  technology sign-off is implied.
- **Source-confirmed** means the behavior follows a specific code path. Its
  production frequency and cost have not been measured.
- **Investigation** means additional sequencing, browser or product-contract
  evidence is required before classifying the issue as a production bug.
- **Opportunity** means a proposed improvement with a measurable acceptance
  target. Several deliberately overlap bugs: they describe the broader fix.

Validation at this baseline:

| Check                                                                        | Result                                                           |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Admin suite, its own Vitest config, one worker                               | **81/81 passed**, 7 files                                        |
| Admin TypeScript, `tsc --noEmit -p apps/admin-web/tsconfig.json`             | Passed                                                           |
| Admin Vite production build                                                  | Passed; reported build time **449 ms**                           |
| Temporary observational probes                                               | **10/10 passed**; removed from repository after evidence capture |
| Live browser, production PostgreSQL, native/mobile and full workspace suites | Not run for this documentation audit                             |

The build emitted eight files totaling **527,664 bytes**. The eager JS entry was
**419,692 bytes** (119,407 bytes with offline Python gzip); CSS was **31,073
bytes** (6,881 bytes with the same compression). Vite's own gzip estimate uses
different compression settings. Font variants are emitted assets, not proof
that every browser fetches every variant. Build time is not page startup time.

The most evident scaling cost is repeated API/server work rather than a huge
initial bundle. [VaultDetail](../../apps/admin-web/src/App.tsx) starts ten API
requests per refresh, normally every five seconds: approximately **120 requests
per minute per visible details page**, excluding initial loads, focus events and
mutations. [PermissionsPage](../../apps/admin-web/src/App.tsx) requests four
collections, then each group's members and each vault's grants: approximately
**12 × (4 + G + V) requests/minute**, where G is groups and V is vaults.
These are source-derived steady-state estimates, not captured traffic.

At 50 groups and 100 vaults that becomes 1,848 requests/minute for one page,
before overlapping loads. The server's configured default REST budget is 1,200
per minute ([config](../../crates/collab-server/src/config.rs)); verify the
effective rate-limit key, settings and concurrent clients before predicting
which requests receive 429. Simply raising that budget would retain the work.

## Existing Safeguards To Preserve

The audit does not assume optimization means removing work indiscriminately:

- Hidden tabs skip interval polling; the hook already avoids rebuilding timers
  merely because callback identity changes.
- Current server permission/capability checks and browser CSRF/session cookies
  remain authoritative. A stale admin page is not an authorization bypass.
- Avatar size validation precedes base64 conversion. Password reset tokens are
  removed from the fragment after initialization; reset forms have pending and
  input guards. Appearance storage is not bearer-token storage.
- Backup uploads already use raw archive transfer with byte progress. The UI
  distinguishes transfer completion from indeterminate server processing and
  suppresses backup polling during active operations.
- Download object URLs are revoked by current consumers. Fix buffer/lifetime
  issues without discarding that cleanup.
- Caddy already supplies compression and security headers. Existing channel
  loaders include identity/epoch checks, bounded pages and stable retry IDs;
  compare shared findings with the [desktop audit](./desktop-performance-and-bugs-2026-10-14.md).

## Suggested Implementation Order

1. **Correctness/accessibility:** WB01–WB09; central auth/error handling,
   preference write ordering and preserving dirty drafts. Add regression tests
   that assert desired behavior, replacing observational bad-behavior probes.
2. **API scaling:** visible-pane loads, aggregate permissions/subject queries,
   delta manifests, pagination and expensive dashboard summary caching. Capture
   server/DB and request baselines before changing endpoint contracts.
3. **Transfer bounds:** binary vault imports, streamed backup/file responses,
